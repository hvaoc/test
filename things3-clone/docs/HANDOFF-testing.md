## ★ USER DIRECTIVES — implement these (2026-07-07)

1. **Do NOT relaunch the app / clearState for every test.** Launch + clear state **once per
   whole run**, not per test. The current Maestro flows each do `launchApp: {clearState:true}`
   — that cold-loads the RN bundle + CRDT/OPFS hydration every flow (~5s each) and is the main
   reason mobile is slow (~25s/flow).
2. **Group tests that live on the same screen together**, so a group navigates/prepares data
   ONCE and runs several checks without re-navigating or re-seeding per test.
3. **Apples-to-apples report.** The matrix must have the **same granularity across all 4
   flavors**. Web (Playwright) currently = **21 individual test cases** across 7 spec files;
   mobile (Maestro) currently = **7 flows** (1 per feature group). Make them line up: the
   report should show the **same test list** for web/desktop/iOS/android. Optimizing *how*
   they run (grouping, single launch) is encouraged, but the **granularity must match**.

### How to implement the mobile optimization (Maestro)
- Use a **master flow per screen/feature group** that `launchApp` ONCE (no clearState inside
  sub-flows), then `- runFlow: <sub>.yaml` for each individual check. Maestro `runFlow`
  executes a sub-flow **without relaunching** the app.
- Reset state **once** at run start (a single `launchApp: {clearState:true}` in a first
  `setup` flow, or `clearState` only on the master flow's first launch).
- Between checks in a group, return to a known screen via testID nav (e.g. `list-back`)
  instead of relaunching.
- Emit **per-check** results (one JSON entry per individual test case, matching the 21 web
  cases) so `maestro-report.sh` / the report show the same rows as web.
  → Either split into ~21 named sub-flows, or run one flow and record labeled sub-results.
- Mirror the exact web test names (see `e2e/tests/*.spec.ts`) so rows map 1:1.

### Report generator change for apples-to-apples
- `scripts/gen-test-report.mjs` should build ONE canonical test list (the 21 web cases,
  grouped by feature) and render every flavor against it. Mobile JSON must key results by the
  same case names. Missing per-flavor cases render "not run", not a different row set.

## GOTCHAS THAT COST HOURS (do not rediscover)
1. **Gradle caches the JS bundle.** `assembleRelease` marked the bundle task "up-to-date" and
   shipped an OLD bundle WITHOUT new testIDs (app renders, testIDs absent). **Fix:** delete
   `android/app/build/generated/assets/createBundleReleaseJsAndAssets` +
   `android/app/build/intermediates/assets`, build with `--rerun-tasks`. iOS xcodebuild
   re-bundles fresh (less prone).
2. **Emulator ANR under load.** Running iOS + Android suites concurrently starved the machine →
   "System UI / Pixel Launcher isn't responding" dialogs blocked Maestro (false 0/7), and once
   **crashed the emulator** (`device not found`). **RUN ONE DEVICE AT A TIME.** Reboot:
   `emulator -avd things_avd -no-snapshot-save -no-audio`.
3. **Maestro iOS driver is slow to restart** after you kill a hung run (~1–1.5 min XCTest
   rebuild). Don't wrap runs in a 2-min bash timeout — use `run_in_background`.
4. **iOS `hideKeyboard` unreliable**; **`scrollUntilVisible` can loop on iOS bottom sheets** —
   use fixed `- swipe: {direction: UP}` instead.
5. **AnchoredPopover bug (FIXED)**: detail When/Priority popover had a backdrop `Pressable` that
   swallowed option taps on iOS/web (RN stopPropagation doesn't block parent onPress). Fixed in
   `TaskDetailModal.js` → backdrop is now a sibling behind the card. (Same bug made Playwright
   skip the priority-condition custom view.)

## MOBILE UX FACTS (differ from web — flows must account for these)
- The "+" **FAB opens the task DETAIL editor** ("New To-Do"), NOT an inline composer. FAB opens
  with keyboard DOWN, so detail field rows are directly tappable.
- Tapping a sidebar list PUSHES a screen; back = `list-back` (list) / `detail-back` (detail),
  NOT the iOS system back.
- Detail When/Priority = anchored popover menus (`when-menu-*`, `pri-menu-*`), distinct from the
  composer's bottom sheets (`WhenSheet`/`PrioritySheet`).
- **Settings**: the full Settings sheet is **sign-in-gated** (offline the account row opens
  login). The only offline-reachable setting is show-completed via the per-list **Display** menu
  (`list-display` → `setting-show-completed` → close `display-backdrop`) — and Display only
  renders **inside a Project**. That's why the settings flow creates+opens a project.
- Query-builder condition FIELD dropdown is **clipped inside the bottom sheet** on web+mobile
  (known bug) → custom-view uses the **text-filter path** (`qb-text`). Operator logic is covered
  by the engine matrix.
