How the app stores & syncs your data

A plain‑English tour of the “data layer”: where your to‑dos live, how the app keeps working with no internet, and how your phone, laptop and browser all stay in agreement — automatically.

1The big idea: local first, sync later

Most apps talk to a server for every little thing. If the internet hiccups, they spin or break. This app flips that around:

Golden rule Every change is saved to a database on your own device first. That’s instant and works with no internet. Syncing with the server happens quietly in the background whenever a connection is available.

Because each device has a full copy of the data, the app is always fast and always available. The only remaining question is: “when two devices change the same thing, who wins?” — and the app answers that automatically using a technique called a CRDT (more on that soon).

2The four building blocks

🗃️ Local database (SQLite)

A tiny, reliable database that lives right on the device. Your to‑dos are stored here. Reading & writing never needs the network.

⚙️ The CRDT engine

The “brain.” It turns your edits into tiny records of what changed, and knows how to merge changes from other devices without conflicts.

📜 The change log (“oplog”)

A queue of your recent changes waiting to be sent up. Think of it as an outbox of small notes like “set task 12’s title to ‘Buy milk’.”

☁️ The sync server (a relay)

A simple mailbox in the cloud. It stores and forwards each user’s change‑notes to their other devices. It never decides who wins — the engine does.

Why a “relay” and not a smart server? Keeping the server dumb (just store & forward) makes it simple and hard to get wrong. All the cleverness (merging) lives in the identical engine on every device, so every device reaches the exact same result on its own.

4One engine, two homes

The clever part: the engine is written once, in Go. But it needs to run in two very different places — a native app and a web browser. So it lives in two forms:

Desktop & Mobile

Served by a Go binary

The Go engine runs natively and owns a real SQLite file on disk directly. The screen (a WebView on desktop, React Native on mobile) simply calls into it. No WASM required.

Web browser

Go → WASM, in a Worker

Browsers can’t run a Go binary, so the same Go engine is compiled to WASM and runs inside a background Web Worker. It stores data in SQLite‑WASM using private browser files (OPFS).

5Getting back online: the sync cycle

When a connection is available, each device runs a simple two‑step exchange with the relay server: push my outbox up, then pull everyone else’s changes down.

Sequence · one sync cycle
sequenceDiagram
  autonumber
  participant C as Your device
  participant S as Sync server (relay)
  Note over C: connection available → sync
  C->>S: PUSH my outbox (list of change‑notes)
  S-->>C: got them ✅ (outbox can be cleared)
  C->>S: PULL changes since my last sync
  S-->>C: here are other devices' change‑notes
  C->>C: merge them in — automatically (CRDT rules)
  Note over C,S: The server only stores & forwards notes.
It never decides who "wins".

To make this real‑time, the server also keeps a live line open (a WebSocket): the instant another device pushes a change, your device gets a nudge and pulls immediately — so edits appear on all your screens within moments.

6Two devices, one conflict — solved automatically

This is the scenario that breaks naïve apps. Two devices edit the same to‑do while both are offline. What happens when they sync?

Sequence · concurrent edits merge cleanly
sequenceDiagram
  autonumber
  participant P as 📱 Phone
  participant S as ☁️ Server
  participant L as 💻 Laptop
  Note over P,L: Same task. Both offline.
  P->>P: change the TITLE
  L->>L: change the DUE DATE
  Note over P,L: later… both come online
  P->>S: push (title change)
  L->>S: push (due‑date change)
  S-->>L: pull → receives phone's title change
  S-->>P: pull → receives laptop's due‑date change
  Note over P,L: Different fields → BOTH kept. ✅
Same field twice → the newer timestamp wins,
and every device picks the SAME winner.
The trick behind “automatic” The engine tracks changes per field (title, due date, priority…) instead of per whole to‑do. Each change carries a special timestamp called an HLC that works even when device clocks disagree. So merging is just: for each field, keep the change with the latest HLC — a rule every device applies identically, arriving at the same answer with no server, no locking, and no “sync conflict” pop‑ups.

7Glossary — the tech, in plain terms

Each row: what it is, and — more importantly — what problem it solves.

TermIn one sentenceWhy we use it / the problem it solves
CRDTConflict‑free Replicated Data Type A way of storing data so that many copies can be edited independently and later merged automatically, always landing on the same result. Two devices editing offline would normally clash. A CRDT guarantees they merge with no conflicts and no central referee — the heart of offline‑first.
HLCHybrid Logical Clock A smart timestamp = real time + a small counter + the device’s ID. Device clocks disagree (“clock skew”). A plain timestamp would let a device with a fast clock always win. HLC gives a fair, consistent order and a tie‑breaker, so every device picks the same winner.
Op & oplogoperation & operation log An “op” is one tiny recorded change (“set task 12’s title to X at time T”). The oplog is the outbox of ops waiting to sync. Sending whole documents is wasteful and overwrites other people’s edits. Shipping small, precise ops lets devices merge exactly what changed.
SQLite A tiny, rock‑solid database that lives in a single file — no separate database server needed. We need durable local storage with real queries and safe transactions. SQLite is the world’s most‑used embedded database; it’s the same on every platform here.
WASMWebAssembly A way to run code written in languages like Go or C inside a web browser, at near‑native speed. Our engine is written in Go, but browsers only run JavaScript. WASM lets the exact same Go engine run in the browser — so we don’t have to rewrite and maintain a second copy in JS.
Web Worker A background thread in the browser, separate from the one that draws the screen. Heavy work (crunching tens of thousands of changes) on the main thread would freeze the UI. A worker runs it in the background so the app stays smooth.
OPFSOrigin Private File System A private, fast, sandboxed file area the browser gives to each website. SQLite needs real files to store its database, but browsers don’t hand out normal disk access. OPFS provides fast, private files that SQLite‑WASM can read and write.
SAHPool VFSSync Access Handle Pool The specific method SQLite‑WASM uses to talk to OPFS: a pool of synchronous file handles. It lets SQLite read/write OPFS synchronously inside a worker without needing shared memory or the special COOP/COEP headers below — which keeps deployment simple.
COOPCross‑Origin‑Opener‑Policy An HTTP header that isolates your page from other browser tabs/windows. It’s one of the two switches that unlock “cross‑origin isolation” — a secure mode required for powerful features like shared memory (below).
COEPCross‑Origin‑Embedder‑Policy The partner HTTP header that controls what resources your page is allowed to load. COOP + COEP together turn on cross‑origin isolation. We deliberately avoid needing them by choosing the SAHPool method above — fewer server headers to configure, and it works out of the box.
SharedArrayBuffer A block of memory that two threads can read/write at the same time. The older/faster way to use OPFS relied on this, and it’s locked behind COOP+COEP for security. Since we sidestep it, we mention it only so the COOP/COEP names make sense.
Relay server A simple cloud service that stores each user’s ops and forwards them to their other devices. Devices need a common meeting point to swap changes. Keeping it “dumb” (store & forward only) makes it simple and reliable; the merging is done by each device’s engine.
Wails & gomobile Tools that package the Go engine into a real desktop app (Wails) and mobile libraries (gomobile). They let the same Go code ship as a native Mac/Windows app and inside iOS/Android apps — no WASM needed there, since Go runs natively.
The whole story in one breath Your edits are saved instantly to a local SQLite database and logged as small ops. The same Go CRDT engine runs everywhere — natively on desktop/mobile, and as WASM in a Web Worker (with OPFS storage) on the web. When online, devices push/pull ops through a dumb relay server and merge them automatically using HLC timestamps — so everything works offline and every device always agrees.
