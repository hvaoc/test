Record sync engine · design note

Deleting is easy. Forgetting a delete is the hard part.

How the structured-data op-log handles deletes across devices — why a naïve “clean up deleted rows” corrupts stragglers, and the two-part fix (a retention window on the server plus a server-issued cursor-expiry) that keeps every client correct no matter how long it was gone.

The cast. Two of one user’s devices and the server, which stores the tenant’s record_registers (one row per field, highest-HLC wins). Deleting task t1 isn’t a SQL DELETE — it’s a CRDT op presence(t1)=false. That surviving “not present” row is the tombstone: the only thing that carries the fact “this was deleted” to devices that haven’t heard yet.

sync / pull delete op (tombstone) divergence / bug converged cursor = “I’ve applied ops up to seq N”

01The happy path — a delete reaches everyone

All devices online. The delete is pushed, stored as a tombstone, and pulled by the other device before anything is cleaned up.

Why it works: the tombstone is still on the server when the phone pulls, so the “deleted” fact reaches it. Nothing is cleaned up too soon.

02The bug — garbage-collect the tombstone too soon

The phone is offline when the delete happens. A cleanup job removes the tombstone before the phone ever reads it. The delete is lost to that device — forever.

Root cause: the tombstone is the carrier of the deletion. Delete it before a lagging device reads it, and that device is stranded showing a ghost task.

03The fix — retention window + a server-issued cursor-expiry

Keep tombstones for a retention window (35 days). The server stamps a GC watermark — the highest seq it has ever reclaimed — and returns cursorExpired to any client whose cursor sits below it. Caught-up devices pull the retained tombstone; long-gone devices wipe and full-reload. The client’s clock is never in the trust path.

Why both lanes are safe: if you synced within the window, any delete you missed is younger than your gap, so it’s still retained — you pull it. If your gap is longer, you don’t trust your cursor at all: you rebuild from scratch, and the deleted task simply isn’t in the copy.

Why a server watermark beats a client clock: the server already numbers every change with a monotonic seq, and the cursor is a seq. So “has this device fallen behind the purge?” is the exact test cursor < watermark — no wall-clock, no last_sync_at, no skew, no dependence on a device’s (possibly wrong) clock. A device off for 34 days whose cursor still clears the watermark stays on the cheap incremental path; a pure time rule would have force-reloaded it for nothing.

04The whole mechanism, on two index cards

Server

  • Store deletes as tombstones (present=false) with a server-clock deleted_at.
  • Hourly job: DELETE … WHERE present=false AND deleted_at < now() − 35 days, plus a sweep of field/elem rows orphaned by a purged entity.
  • Each purge raises a per-tenant gc_watermark = the highest seq it just reclaimed. That one number is the whole client-facing contract — no per-client tracking.
  • On pull: cursor>0 AND cursor<watermark → return cursorExpired; else return deltas (seq>cursor). A full (cursor 0) pull floors its returned cursor at the watermark so the client can’t loop-expire.
  • Retention (35d) is just slack over the advisory client hint (30d); correctness rides on the watermark, not the interval.

Client

  • The cursor is the only sync state that must persist — device-scoped (OPFS), shared across tabs by the leader, never per-tab.
  • Normal path: incremental pull(cursor) → apply ops (including any retained tombstones) → advance cursor.
  • Server said cursorExpired → reconcile pending (push offline creates + edits to still-living entities; drop edits to vanished ones), then wipe local & full-pull from cursor 0.
  • Reconstruction shows an entity only if it has a present=true presence row — an orphan field row is invisible, never a ghost.
  • Optional: a local now − last_sync > 30d check may pre-empt a doomed incremental round-trip, but it is advisory only.

This trades the textbook “track every client’s version vector” for “one timestamp on each side and a full reload for anyone who’s been gone too long” — which is what most production sync systems actually ship. The op-log stays bounded, deletes never strand a straggler, and the server never has to know who’s listening.

05The logic, in code

Two moving parts: the server forgets old tombstones on a timer; the client decides, on each reconnect, whether its cursor is still trustworthy.

Server · schema + GC job (runs hourly)SQL
-- stamp the SERVER clock when a row becomes a tombstone (never the op's HLC)
ALTER TABLE record_registers ADD COLUMN deleted_at timestamptz;
--   on every applied op:  deleted_at = present ? NULL : now()
--   (a newer tombstone only re-stamps LATER — retention can move out, never in)

-- one row per tenant: the highest seq the GC has ever reclaimed
CREATE TABLE record_gc ( scope TEXT PRIMARY KEY, watermark BIGINT NOT NULL DEFAULT 0 );

-- GC job — retention (35d) is slack over the client hint (30d); correctness
-- rides on the watermark, not the interval. One statement, three CTEs:
WITH purged AS (                          -- 1 · forget tombstones past the window
  DELETE FROM record_registers
   WHERE present = false AND deleted_at < now() - interval '35 days'
  RETURNING scope, seq ),
swept AS (                               -- 2 · sweep field/elem rows of a purged entity
  DELETE FROM record_registers r
   WHERE r.field <> ''
     AND NOT EXISTS (SELECT 1 FROM record_registers p
                      WHERE p.scope=r.scope AND p.kind=r.kind
                        AND p.entity=r.entity AND p.field='')
  RETURNING scope, seq ),
reclaimed AS (
  SELECT scope, max(seq) AS hi
    FROM (SELECT * FROM purged UNION ALL SELECT * FROM swept) u
   GROUP BY scope )
INSERT INTO record_gc (scope, watermark)  -- 3 · raise each tenant's watermark
SELECT scope, hi FROM reclaimed
ON CONFLICT (scope) DO UPDATE
  SET watermark = GREATEST(record_gc.watermark, EXCLUDED.watermark);
Server · pull (the cursor-expiry gate)Go
w := watermarkFor(scope)                    // SELECT watermark FROM record_gc WHERE scope=…
if cursor > 0 && cursor < w {
    respond({ cursorExpired: true })        // behind the purge — its view can't be trusted
    return
}
ops, newCursor := rowsWhere(seq > cursor)   // cursor 0 ⇒ the whole current copy
if cursor == 0 && newCursor < w {           // GUARDRAIL: a full copy whose newest live rows
    newCursor = w                           // sit below a purged tombstone's seq would else
}                                           // loop-expire on the very next pull. Floor it.
respond({ ops, cursor: newCursor })
Client · on reconnectJS
async function sync() {
  const res = await pull({ cursor });        // server compares cursor vs its gc-watermark
  if (res.cursorExpired) return fullReload();   // gone past the purge — cursor untrustworthy
  await applyRemote(res.ops);              // LWW-merge; includes any retained tombstones
  setCursor(res.cursor);                     // the cursor is the ONLY persisted sync state
}

async function fullReload() {              // authoritative recovery — no clock involved
  const full = await pull({ cursor: 0 });    // 1 · whole current copy (deleted rows absent)
  await reconcilePending(full);             // 2 · keep creates + edits to LIVING entities…
  await wipeLocalRecords();                 // 3 · drop stale local state, incl. ghosts
  await applyRemote(full.ops);              // 4 · rebuild from the copy
  setCursor(full.cursor);
}

// Anti-resurrection: never re-push an edit to an entity the server no longer has,
// unless WE created it offline — else a stale field write revives a deleted task.
function reconcilePending(full) {
  const live = new Set(full.ops
    .filter(o => o.t === 'presence' && o.p)
    .map(o => o.k + ':' + o.i));
  const keep = pending.filter(op =>
       (op.t === 'presence' && op.p)     // our own offline creations — always keep
    || live.has(op.k + ':' + op.i));     // edits to something still alive
  return pushOps(keep);                      // edits to vanished entities are dropped
}

One subtlety the wiring pinned down: a field-value row travels with present=false on the wire, so the tombstone predicate is present=false AND (field='' OR elem<>'') — value rows are values, never tombstones.

06The late-write trap — and why a delete can’t be resurrected

Retention protects a device that needs to read a delete. The remaining hazard is a device that wrote to an entity that was deleted — and stayed offline past the retention window.

Picture a phone offline 40 days that edited t1.title locally. t1 was deleted on day 0; its presence tombstone was purged on day 35. Presence and field are independent LWW registers, so a naïvely re-pushed title op (with a fresher HLC than the long-gone delete) would land as a title row with no presence row left to gate it — a partial “zombie.” Three independent layers stop it, so no single miss revives a task:

At the source (client)

  • reconcilePending drops any field/set edit whose entity is absent from the fresh full copy — unless the client created it offline. The zombie op is never sent.

In view (reconstruction)

  • Materialize emits an entity only with a present=true presence row (snapshot.go skips the rest). An orphan field row is invisible — never a ghost.
  • Invariant: the JS reconstruction in record.worker.js must apply the same presence-required rule. Pin it with a shared cross-impl test.
Backstop: should a zombie field row ever reach Postgres anyway, the GC’s orphan sweep reclaims it within the hour (and lifts the watermark), so it can neither accumulate nor leak. The same sweep is what reclaims a deleted task’s ordinary field rows once its presence tombstone is purged — which is why Requirement 1 stays bounded.

07Decisions — the record we’re committing to

Everything above, distilled to the choices a future reader (or a re-implementation) shouldn’t re-litigate — grouped by the two requirements they satisfy.

Req 1 · the DB never leaks deletes

  • D1 Deletes are tombstones (present=false) carrying a server-clock deleted_at — set present ? NULL : now() on every applied op.
  • D2 Hourly GC purges tombstones older than 35 days, then sweeps field/elem rows orphaned by a purged entity. A startup backfill stamps pre-column tombstones so legacy deletes can’t leak.
  • D3 Steady-state size = live registers + ≤ 35 days of tombstones + ≤ 1 hour of orphans. Bounded, not unbounded.

Req 2 · every client learns every delete

  • D4 The authoritative staleness signal is the server’s per-tenant gc-watermark (max seq ever reclaimed); Pull returns cursorExpired when cursor < watermark. The client clock is never in the trust path.
  • D5 Recent client (cursor ≥ watermark) → incremental pull carries the retained tombstone. Long-gone client → cursorExpired → wipe + full reload, deleted rows simply absent.
  • D6 A local now − last_sync > 30d hint is advisory only — it may skip a doomed round-trip, never decides correctness.

Correctness guardrails

  • D7 The watermark is per-scope (seq is per-tenant) and rises from tombstone purge and orphan sweep.
  • D8 A full (cursor 0) pull floors its returned cursor at the watermark, or a client whose newest live rows predate a purged tombstone would loop-expire forever.
  • D9 Full-reload pull must paginate by seq range — a cursor-0 copy of a 1M-entity tenant can’t ship in one response.

Client guardrails

  • D10 The cursor is the only persisted sync state; device-scoped (OPFS), shared across tabs by the leader — not per-tab.
  • D11 Full reload runs reconcilePending first (see §06) so recovery can’t resurrect a deleted entity.
  • D12 Reconstruction requires a present=true presence row — matched in snapshot.go (Go) and record.worker.js (JS).
Why this is fool-proof for an absence of any length. Take a client gone for a gap g. Either no tombstone it still needs has been purged (cursor ≥ watermark) and the incremental pull carries every missed delete — or one has (cursor < watermark) and the server refuses to trust the cursor, forcing a from-scratch copy in which deleted entities don’t exist. There is no value of g that silently drops a delete. (The ygo notes/settings layer keeps its own delete-set, so it never faced this trade.)
