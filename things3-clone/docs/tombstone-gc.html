Record sync engine · design note

Deleting is easy. Forgetting a delete is the hard part.

How the structured-data op-log handles deletes across devices — why a naïve “clean up deleted rows” corrupts stragglers, and the retention-window fix that keeps it correct.

The cast. Two of one user’s devices and the server, which stores the tenant’s record_registers (one row per field, highest-HLC wins). Deleting task t1 isn’t a SQL DELETE — it’s a CRDT op presence(t1)=false. That surviving “not present” row is the tombstone: the only thing that carries the fact “this was deleted” to devices that haven’t heard yet.

sync / pull delete op (tombstone) divergence / bug converged cursor = “I’ve applied ops up to seq N”

01The happy path — a delete reaches everyone

All devices online. The delete is pushed, stored as a tombstone, and pulled by the other device before anything is cleaned up.

Why it works: the tombstone is still on the server when the phone pulls, so the “deleted” fact reaches it. Nothing is cleaned up too soon.

02The bug — garbage-collect the tombstone too soon

The phone is offline when the delete happens. A cleanup job removes the tombstone before the phone ever reads it. The delete is lost to that device — forever.

Root cause: the tombstone is the carrier of the deletion. Delete it before a lagging device reads it, and that device is stranded showing a ghost task.

03The fix — retention window + a “how long have I been gone?” check

Keep tombstones for a retention window (say 35 days). Each client remembers when it last synced. On reconnect it picks its lane: caught up recently → incremental; gone too long → full reload.

Why both lanes are safe: if you synced within the window, any delete you missed is younger than your gap, so it’s still retained — you pull it. If your gap is longer, you don’t trust your cursor at all: you rebuild from scratch, and the deleted task simply isn’t in the copy.

The one subtlety: track “last time I successfully synced” — the last time you reached the server — not the age of your newest op. A workspace nobody touched for 40 days is still fresh if you synced yesterday and got nothing new.

04The whole mechanism, on two index cards

Server

  • Store deletes as tombstones (present=false) with a deleted_at timestamp.
  • Background job: DELETE … WHERE present=false AND deleted_at < now() − 35 days, plus a sweep of orphaned field rows.
  • No per-client tracking, no watermark. Just purge by age.
  • Retention window is deliberately longer than the client threshold (35 > 30) — slack for skew & sync latency.

Client

  • Keep one value: last_sync_at, set to now on every successful pull (even an empty one).
  • On reconnect: now − last_sync_at ≤ 30d → normal incremental pull.
  • Otherwise → push pending edits first (don’t lose offline work), then wipe local & full-pull from cursor 0.
  • Optional hardening: measure the gap in server time (returned in the pull) so a wrong device clock can’t fool it.

This trades the textbook “track every client’s version vector” for “one timestamp on each side and a full reload for anyone who’s been gone too long” — which is what most production sync systems actually ship. The op-log stays bounded, deletes never strand a straggler, and the server never has to know who’s listening.

05The logic, in code

Two moving parts: the server forgets old tombstones on a timer; the client decides, on each reconnect, whether its cursor is still trustworthy.

Server · GC job (runs hourly)SQL
-- stamp the SERVER clock when a row becomes a tombstone (not the op's HLC)
ALTER TABLE record_registers ADD COLUMN deleted_at timestamptz;
--   on push:  present = false  →  deleted_at = now()

-- GC job — retention MUST exceed the client threshold (35 > 30) for slack.
-- 1 · forget tombstones older than the window
DELETE FROM record_registers
 WHERE present = false
   AND deleted_at < now() - interval '35 days';

-- 2 · sweep field/tag rows orphaned by a purged entity (no presence row left)
DELETE FROM record_registers r
 WHERE r.field <> ''
   AND NOT EXISTS (
     SELECT 1 FROM record_registers p
      WHERE p.scope = r.scope AND p.kind = r.kind
        AND p.entity = r.entity AND p.field = '');
Client · on reconnectJS
const THRESHOLD = 30 * 864e5;              // 30 days  (< server's 35-day retention)

async function sync() {
  const gap = Date.now() - lastSyncAt;     // time since we last reached the server
  await (gap > THRESHOLD ? fullReload() : incrementalPull());
  lastSyncAt = Date.now();                 // stamp EVERY successful sync (even empty)
}

async function incrementalPull() {
  await pushPending();                     // send our local ops first
  const { ops, cursor } = await pull({ cursor });
  await applyRemote(ops);                  // LWW-merge — includes any tombstones
  setCursor(cursor);
}

async function fullReload() {              // gone too long: don't trust the cursor
  await pushPending();                     // 1 · don't lose offline edits
  const full = await pull({ cursor: 0 });  // 2 · fetch the whole current copy
  await wipeLocalRecords();                // 3 · drop stale local state
  await applyRemote(full.ops);             // 4 · rebuild — deleted rows simply absent
  setCursor(full.cursor);
}

Not wired yet. This is the design. The live record_registers table has no deleted_at column and keeps tombstones indefinitely — adding this GC job + the client’s last_sync_at check is the remaining work.
