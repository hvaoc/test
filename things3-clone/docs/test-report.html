3 · Coverage & honest caveats

What is measured vs. not, and why:
  • Native engine (desktop/iOS/Android) @ 1k and 1M — MEASURED. Same Go core/record engine, all 23 operations, all within budget at 1M.
  • Web feature E2E @ normal — MEASURED (Playwright, 21 tests).
  • Web engine @ 1M — NOT benchmarked this run. The web SQLite-WASM engine (public/record.worker.js) still carries the pre-optimization schema (FTS id UNINDEXED, missing when/deadline/priority + partial-open indexes) — the same bugs fixed in the Go engine but not yet ported to JS. So web @ 1M is expected to be sluggish on writes/search/Today until those fixes are ported. Not faked as a pass.
  • Mobile E2E: run on the real iOS Simulator + Android emulator via Maestro, split into the same 21 cases as web (see .maestro/cases.json). The whole suite runs in one app session — a single launch + clearState, then every case flow attaches to the already-open app (no per-test relaunch), so the ~60s cold start is paid once instead of 21×. One case — "add a Heading" — has no phone UI (the "Add section" trigger is a wide-layout-only affordance) and is honestly marked n/a rather than faked. When/Priority, which the RN-Web build couldn't drive via the detail popover on web, are driven there on mobile (the AnchoredPopover fix landed).
  • Desktop uses the same expo-web bundle as web (Wails serves it), so its UI cells mirror web; its non-UI Go path is covered by the coordinator Go tests (all green).
